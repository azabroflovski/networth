# Roadmap

## Реализовано

**Этап 1 — фундамент** (2026-11-11)

- Elixir-приложение: Plug + Bandit, Postgrex, SQL-миграции и mix-задачи `db.*`.
- Регистрация, вход, bearer-токены, выход. Личный workspace создаётся при регистрации в той же транзакции.
- Workspaces: создание, изменение имени и часового пояса (owner), список участников, приглашения по email (создать, отозвать, принять).
- Счета: 7 пользовательских типов, начальный остаток через ledger, переименование, архив, балансы из проводок.
- Ledger: expense, income, transfer, exchange (с курсом и деталями), opening_balance, reversal; история с фильтрами.
- Категории с одним уровнем подкатегорий, системные категории по умолчанию, архив.
- Теги: CRUD, цвет, привязка к операции, замена тегов у проведённой операции.
- Инварианты в БД: баланс по валютам, неизменность ledger, принадлежность workspace, валюта счёта, однократное сторно, категория только на проводке подходящего счёта.
- Идентификаторы — UUIDv7 (DECISIONS 4).

**Уточнение финансовой модели** (2026-11-11)

- Split: категория на строке расхода/дохода, одна операция может иметь несколько категорий (DECISIONS 7).
- Часовой пояс workspace; даты по умолчанию — сегодня в нём (DECISIONS 18).
- Сторно по умолчанию датируется датой исходной операции; повторное сторно возвращает существующее (DECISIONS 10).
- Идемпотентность: тот же ключ с другими параметрами — 409 (DECISIONS 14).
- 83 теста (ExUnit, реальная PostgreSQL): регистрация, workspaces, часовые пояса, доступ, изоляция, проводки, split, переводы, валюты, сторно, идемпотентность, откат, конкурентность, категории и теги, HTTP.

## Текущий этап

Модель ledger зафиксирована. Следующий этап — отчёты.

## Следующие задачи

По приоритету:

1. **Отчёты.** Доходы/расходы по категориям за период в каждой валюте — сумма `ledger_entries.amount` по `category_id` (сторно учитываются сами, DECISIONS 7); баланс счёта на дату; движение по счёту за период. Периоды — в часовом поясе workspace. Только чтение, новый модуль `Networth.Reports`.
2. **Исправление описания.** Решить: только сторно + новая операция (как сейчас) или разрешить менять описание с журналом изменений. Проводки и категории неизменны в любом случае.
3. **Управление участниками:** удалить участника, выйти из workspace, передать владение (инвариант: хотя бы один owner).
4. **Id операции от клиента** — для офлайн-ввода и черновиков AI: необязательный `id` в `Ledger.post/2`; повтор с существующим id — конфликт, а не повторное проведение (идемпотентность остаётся за `idempotency_key`).
5. **Идемпотентность создания счёта** (сейчас дубль отсекает только уникальность имени).
6. **Пагинация по курсору** для истории операций вместо `offset`.
7. **Сводка капитала:** активы − обязательства по каждой валюте.
8. **Бюджеты** по категориям на период.
9. **Долги:** кому и сколько должен / должны мне — вероятно, как liability/asset-счета с контрагентом.
10. **Комиссия обмена** отдельной проводкой в expense.
11. **AI-ввод** — адаптер поверх `Ledger.post/2` (DECISIONS 19).

Инфраструктура: CI с PostgreSQL, release-конфигурация, очистка истёкших токенов, ограничение частоты попыток входа.

## Известные ограничения

- Нет UI; только JSON API.
- Нельзя изменить описание или категории проведённой операции без сторно.
- Идемпотентность сверяет точное содержимое запроса: `"100"` и `"100.00"` с одним ключом — конфликт.
- Нет ограничения попыток входа и очистки истёкших токенов.
- Приглашения не истекают, писем нет.
- Нет удаления участников и workspaces.
- Справочник валют меняется только миграцией.
- БД не запрещает добавить сбалансированные проводки к ранее проведённой операции в отдельной транзакции (код этого не делает; DOMAIN «Финансовые инварианты»).
- `offset`-пагинация.
- Миграции пока правятся на месте (развёрнутых баз нет); после первого развёртывания — только новыми файлами.
