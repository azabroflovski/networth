# Решения

Формат: решение — почему — что рассматривали. Новые решения добавляются в конец с номером.

## 1. Plug + Bandit без Phoenix

API — JSON без HTML, каналов и LiveView. Plug.Router покрывает маршрутизацию, Plug.Parsers — JSON. Phoenix добавил бы структуру и зависимости, которые не используются.

## 2. Postgrex и явный SQL, без Ecto

Финансовая логика опирается на возможности PostgreSQL (составные FK, отложенные триггеры, `ON CONFLICT`, `FOR UPDATE`), и их проще читать в виде SQL, чем через DSL. Ecto changesets дублировали бы проверки, которые уже есть в `Params` и в БД.

Цена: нет sandbox для тестов (см. 17), строки возвращаются как map без схем. Текущее соединение транзакции хранится в словаре процесса (`Networth.DB.transaction/1`) — тот же приём использует Ecto; иначе соединение пришлось бы передавать через все доменные функции.

## 3. Свой SQL-мигратор

~130 строк вместо ecto_sql. Миграции — чистые SQL-файлы, выполняются через simple query protocol, поэтому в одном файле можно писать функции и триггеры, а файл применяется атомарно. Только вперёд.

## 4. Идентификаторы — UUIDv7

Тип `uuid`, `DEFAULT uuidv7()` (встроена в PostgreSQL 18), во всех таблицах с суррогатным ключом.

- Последовательный id раскрывает объёмы: `/transactions/1042` говорит, сколько операций во всей системе. Доступа это не даёт, но информация лишняя.
- UUID может сгенерировать клиент (офлайн-ввод, черновики AI-ввода). Сейчас клиент id не передаёт; см. ROADMAP.
- v7, а не v4: v7 упорядочен по времени, вставки идут в конец B-tree индекса, как у bigint; v4 разбрасывает их по индексу. Внутри одного соединения PostgreSQL 18 генерирует v7 монотонно, поэтому проводки одной операции упорядочены по id в порядке вставки.
- 16 байт против 8 для объёмов личных финансов несущественны. Смешивать типы (bigint для `ledger_entries`, которые не видны снаружи) ради этой экономии не стали.
- `idempotency_key` не совмещён с первичным ключом: ключ приходит от клиента, и первичным ключом его делать не стоит.

**UUID в коде — строки, а не 16-байтные binary.** Postgrex без Ecto работает с uuid как с 16 байтами. Вместо преобразования на границе HTTP (каждый id в каждом ответе и каждом параметре) зарегистрирован свой Postgrex-тип (`Networth.UUID` в `Networth.PostgresTypes`): кодирование и декодирование происходят в одном месте, весь код видит одну форму — каноническую строку. Входные id проверяет `Params.cast_id/1`; строка, не являющаяся UUID, превращается в 404/422 до запроса к БД.

Рассматривали bigint `GENERATED ALWAYS AS IDENTITY` (был в первой версии схемы) — отклонён по причинам выше.

## 5. Деньги — bigint минимальных единиц, точность из справочника валют

Целые числа не теряют точность и быстро суммируются. `numeric` тоже точен, но не хранит смысл «минимальная единица валюты», и через него проще случайно сохранить 0.001 USD. Точность валюты — в `currencies.exponent`, не предполагается 2 знака. Внешний формат — десятичная строка, числа JSON отклоняются: float уже мог потерять точность на клиенте.

## 6. Double-entry: суммы со знаком

Одна колонка `amount` (дебет +, кредит −) вместо пары `debit/credit` или `amount + direction`. Инвариант баланса — просто `sum(amount) = 0`, баланс счёта — `sum(amount)`. Знак при показе пользователю определяется `kind` счёта.

## 7. Категории — измерение на строках расхода/дохода, а не счета ledger

**Где категория в ledger**:

- *Категория = счёт ledger* (как в GnuCash): «Еда» — expense-счёт. Счёт имеет одну валюту, значит «Еда» нужна в каждой валюте, подкатегории превращаются в дерево счетов, переименование/архив категории — операция над ledger. Отклонено.
- *Ledger использует системные счета income/expense на валюту, категория — аналитическое измерение* (выбрано). Ledger отвечает за деньги, категории — за аналитику; категории свободно переименовываются и архивируются.

**Где категория в операции** (split, чек «еда + бытовая химия»):

- *A. Одна категория на операцию* (было в первой версии). Чек приходится вводить двумя операциями, которые не совпадают со списанием в выписке банка; исправление — два сторно.
- *B. Категория на строке* (выбрано). `category_id` стоит на проводках по счетам `expense`/`income`, по одной на строку; счёт оплаты получает одну проводку на всю сумму. Отдельной таблицы строк нет: строка и есть проводка, суммам негде разойтись.

Последствия B:
- сторно копирует категории с обратным знаком, поэтому сумма проводок по категории сама учитывает исправления;
- отчёты по категориям считаются по `ledger_entries.category_id`;
- категория — часть неизменяемой проводки: изменить её можно только сторно и новой операцией;
- соответствие категории счёту проверяет БД: на проводке хранится `account_kind` (подтверждён FK на счёт), и FK на категорию по `(workspace_id, category_id, account_kind)` не пропускает категорию на счёте карты или income-категорию на счёте `expense`. Это требование «не смешивать операцию и проводки» не нарушает: операция по-прежнему отдельная сущность, теги — на ней.

## 8. Мультивалютность: баланс по каждой валюте, обмен через системные счета exchange

Сумма проводок обязана быть нулевой в каждой валюте отдельно. Обмен проходит через счёт `exchange` в каждой из двух валют, курс и обе суммы сохраняются в `exchanges`. Альтернатива — хранить проводки в «базовой валюте» workspace — требует автоматической конвертации, что запрещено требованиями и теряет исходные суммы.

Комиссии обмена пока не моделируются: пользователь вводит фактически полученную сумму, разница остаётся в курсе.

## 9. Балансы вычисляются из проводок

Нет хранимого баланса — нечему расходиться с ledger, и конкурентные проводки не требуют блокировок строк счетов. Индекс `ledger_entries (account_id) INCLUDE (amount)` делает подсчёт дешёвым на объёмах личных финансов. Если понадобится, следующий шаг — периодические снимки балансов (balance snapshots), а не мутируемый счётчик.

## 10. Неизменность и сторно

Операции, проводки и детали обмена неизменяемы на уровне БД. Исправление — сторно (зеркальные проводки с теми же категориями, ссылка на исходную) и новая операция. Сторно запрещено сторнировать, чтобы цепочки не ветвились — для «отмены отмены» операцию вводят заново.

**Дата сторно по умолчанию — дата исходной операции.** Сторно у нас означает «запись была ошибкой», поэтому отчёт за период исходной операции должен исправиться. Закрытых периодов в личных финансах нет; момент исправления виден по `inserted_at`. Альтернатива — датировать сегодняшним днём (как в бухгалтерии с закрытыми периодами) — оставляет ошибку в отчёте прошлого месяца. Клиент может передать дату явно. Возврат товара — не сторно, а доход с категорией Refunds.

**Повторное сторно возвращает существующее сторно**, а не ошибку: ретрай клиента, не получившего ответ, должен получить тот же результат. Двойное сторно невозможно (уникальный индекс по `reverses_id`, `FOR UPDATE` на исходную операцию).

Теги можно менять у проведённой операции: они не влияют на деньги и явно исключены из ledger требованиями. Описание тоже можно менять, с журналом (решение 23). Категории, суммы, счета и дата — только через сторно и новую операцию.

## 11. Инварианты баланса — в БД, отложенными триггерами

Проверка в коде недостаточна: любой будущий код или ручной SQL может записать несбалансированные проводки. Отложенный constraint trigger проверяет операцию при COMMIT, когда все проводки уже записаны.

## 12. Изоляция workspaces: Scope + составные FK

Доступ к данным workspace только через `%Scope{}` из `Workspaces.authorize/2`, и все запросы фильтруют по `scope.workspace_id`. Дополнительно составные FK с `workspace_id` не дают записи сослаться на объект чужого workspace, даже если в коде будет ошибка. Row Level Security PostgreSQL не используется: потребовал бы передачи пользователя в сессию БД при каждом запросе; при необходимости можно добавить позже.

Чужой workspace возвращает 404, а не 403, чтобы не раскрывать существование.

## 13. Отрицательные балансы разрешены

Учёт отражает реальность, а не управляет ею: если наличные «ушли в минус», значит, какая-то операция не записана. Блокировка такой записи мешала бы вводу в произвольном порядке и потребовала бы сериализации проводок по счёту.

## 14. Идемпотентность по ключу клиента со сверкой параметров

Уникальный индекс `(workspace_id, idempotency_key)` и `INSERT … ON CONFLICT DO NOTHING`: при конкурентном повторе второй запрос дождётся первого и вернёт его операцию. Вместе с ключом хранится `idempotency_hash` — SHA-256 параметров запроса (`:erlang.term_to_binary(params, [:deterministic])`). Повтор с тем же ключом и другими параметрами — `{:error, :idempotency_key_reused}` (HTTP 409): иначе клиент с ошибкой генерации ключей молча получил бы чужую операцию вместо проведения новой.

Сверяется точное содержимое: `"100"` и `"100.00"` — разные запросы. Ретрай отправляет те же байты, так что это не мешает.

Ключ не совмещён с первичным ключом операции (см. 4). Создание счёта ключа пока не имеет — дубль отсекает уникальность имени.

## 15. Аутентификация: PBKDF2 из :crypto и непрозрачные bearer-токены

PBKDF2-HMAC-SHA256, 600 000 итераций (OWASP), соль 16 байт — встроено в OTP, без NIF-зависимостей bcrypt/argon2. Формат хэша содержит число итераций, поэтому его можно повысить без миграции. Токен — 32 случайных байта, в БД только SHA-256, срок 30 дней. Отзыв — удаление строки. JWT не нужен: проверка всё равно идёт в БД.

## 16. Приглашения по email без отправки писем

Приглашение адресовано email; принять может только пользователь с этим email. Писем нет — приглашённый видит их в API. Токен-ссылки и истечение срока — когда появится отправка писем.

## 17. Тесты на реальной БД с TRUNCATE

Без Ecto нет SQL sandbox. Тесты с БД работают последовательно, таблицы очищаются `TRUNCATE` перед каждым тестом. Это позволяет честно тестировать конкурентность (несколько процессов, несколько соединений), чего sandbox в транзакции не даёт.

## 18. Часовой пояс — у workspace

`workspaces.timezone` (IANA, по умолчанию `UTC`, проверяется по `pg_timezone_names`). Используется для «сегодня» по умолчанию (`occurred_on` операции, `opened_on` начального остатка) и в будущем — для границ периодов в отчётах.

У workspace, а не у пользователя: семейный workspace — общий журнал, и «ноябрь» должен быть одинаковым для всех участников, где бы они ни находились. Клиент по-прежнему может и должен передавать `occurred_on` сам — он знает, что значит «вчера» для пользователя; часовой пояс нужен, когда даты нет.

Дата считается в PostgreSQL (`now() AT TIME ZONE tz`) — у него своя база часовых поясов, зависимость `tzdata` для Elixir не нужна.

## 19. Граница ядра; AI-ввод — отдельный клиент

Финансовое ядро (`Ledger`, `Accounts`, `Categories`, `Tags`, `Workspaces`) не зависит от HTTP: принимает `Scope` и map параметров, возвращает данные или ошибку. HTTP — один из клиентов. Будущий AI-ввод встраивается так же:

1. Адаптер получает текст и контекст workspace (`Accounts.list/1`, `Categories.list/1`, `Tags.list/1`).
2. Провайдер возвращает предложение в формате параметров `Ledger.post/2`; неоднозначные поля остаются пустыми.
3. Пользователь подтверждает предложение.
4. Подтверждение — обычный `Ledger.post/2` с той же валидацией и с `idempotency_key`.

AI не получает доступ к БД и не строит проводки. Специального кода под AI в ядре нет и не нужно.

## 20. Конкурентность без блокировки балансов

Уровень изоляции — READ COMMITTED. Корректность обеспечивают не блокировки счетов, а:

- балансы вычисляются из неизменяемых проводок (решение 9), поэтому одновременные проводки не могут «потерять» обновление;
- уникальные индексы: однократное сторно, `idempotency_key`, один системный счёт на тип и валюту (создаётся через `INSERT … ON CONFLICT DO NOTHING`, затем `SELECT`);
- `FOR UPDATE` на сторнируемую операцию — второе сторно ждёт и видит первое;
- `FOR SHARE` на счета при проведении — архивирование счёта не пересекается с проводкой по нему.

Нарушение отложенного constraint trigger обнаруживается при COMMIT, и DBConnection в этом случае бросает исключение, а не возвращает `{:error, _}`. Код таких проводок не строит, так что это ошибка программы, а не пользовательского ввода.

## 21. Документация: README, DOMAIN, DECISIONS, ROADMAP, AGENTS

Схема БД описана только в миграциях: отдельный документ дублировал бы SQL и расходился с ним. Устройство кода и список API — в README, финансовая модель и инварианты — в DOMAIN. Отказались от PRODUCT, ARCHITECTURE и DATA_MODEL как от лишних на этом этапе.

Правила работы (порядок начала сессии, что обновлять после задачи, принципы, соглашения кода) — в AGENTS.md, а не в разовых промптах: иначе следующая сессия о них не узнает. CLAUDE.md только импортирует AGENTS.md (`@AGENTS.md`), чтобы правила жили в одном месте для любых агентов.

## 22. Отчёты считаются из проводок при каждом запросе

Без материализованных агрегатов и снимков: суммы по индексам `ledger_entries` на объёмах личных финансов дешёвые, а любой кэш пришлось бы поддерживать согласованным с ledger (решение 9). Если запросы станут медленными, следующий шаг — помесячные снимки, а не изменяемые счётчики.

Период фильтруется по `occurred_on`, а не по `inserted_at`: отчёт отвечает на вопрос «сколько потрачено в октябре», а не «сколько записано в октябре». Часовой пояс для этого не нужен — дата уже в календаре workspace (решение 18).

Разбивка по категориям строится из `ledger_entries.category_id` (решение 7), поэтому сторно, split и подкатегории не требуют отдельной логики. Подкатегории сворачиваются в родителя в Elixir, а не в SQL: дерево всего в два уровня, и категорий в workspace немного.

## 23. Описание операции редактируется, изменения пишет журнал в БД

Опечатка в описании не влияет на деньги, а исправлять её через сторно (три записи в истории ради одного слова) неудобно. Поэтому описание — единственное изменяемое поле операции.

**Варианты**:
- *Только сторно и новая операция* — строго, но неудобно для повседневного ввода. Отклонено.
- *Изменение с журналом, журнал пишет приложение* — журнал можно обойти любым `UPDATE` мимо `Ledger.update/3`.
- *Изменение с журналом, журнал пишет триггер* (выбрано). Триггер `transactions_guard` разрешает `UPDATE` только колонки `description` (сравнение `to_jsonb(NEW) - 'description'` со старой строкой, поэтому новые колонки автоматически остаются неизменяемыми) и сам пишет строку в `transaction_changes`. Автора берёт из локальной для транзакции настройки `networth.user_id` (`set_config(..., true)`), которую ставит приложение; без неё изменение отклоняется. Журнал только дополняется.

Одновременные правки сериализуются блокировкой строки, поэтому журнал — непрерывная цепочка: `old_value` каждой записи равно `new_value` предыдущей.

Изменения тегов в журнал не пишутся: теги — пометки для фильтрации, а не история операции. Если понадобится, журнал расширяется значением `field`.

## 24. Хотя бы один owner — проверка в БД с блокировкой workspace

Правило «у workspace есть owner» нарушается гонкой: два owner одновременно выходят, каждый видит второго и проходит проверку. Простая проверка в приложении или в триггере без блокировки этого не ловит (тест `the database keeps an owner under concurrent raw deletes` падает без блокировки).

Отложенный constraint trigger на `workspace_members` перед проверкой берёт `FOR UPDATE` на строку workspace: второе изменение ждёт коммита первого и видит его результат. Функции `Workspaces.update_member/3` и `remove_member/2` берут ту же блокировку в начале транзакции — так пользователь получает понятную ошибку `last_owner` (HTTP 409), а триггер остаётся страховкой для любого другого пути.

Ролей по-прежнему две, все owner равны: любой owner может менять роли и удалять других owner, пока остаётся хотя бы один. Отдельной операции «передать владение» нет: назначить owner другого и затем стать member.
