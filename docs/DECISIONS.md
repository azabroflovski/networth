# Решения

Журнал архитектурных и доменных решений (ADR): решение — почему — что рассматривали.

- Новое решение добавляется в конец со следующим номером и статусом «Принято».
- Записи не переписываются. Если решение меняется, пишется новое, а у старого меняется только статус: «Заменено №N» или «Частично заменено №N». Так видно не только что решено сейчас, но и почему раньше было иначе.
- Решения, помеченные «уточнялось на месте», правились до введения этого правила (2026-11-11); их прежние редакции — в истории git.

## 1. Plug + Bandit без Phoenix

**Статус:** Принято.

API — JSON без HTML, каналов и LiveView. Plug.Router покрывает маршрутизацию, Plug.Parsers — JSON. Phoenix добавил бы структуру и зависимости, которые не используются.

## 2. Postgrex и явный SQL, без Ecto

**Статус:** Принято.

Финансовая логика опирается на возможности PostgreSQL (составные FK, отложенные триггеры, `ON CONFLICT`, `FOR UPDATE`), и их проще читать в виде SQL, чем через DSL. Ecto changesets дублировали бы проверки, которые уже есть в `Params` и в БД.

Цена: нет sandbox для тестов (см. 17), строки возвращаются как map без схем. Текущее соединение транзакции хранится в словаре процесса (`Networth.DB.transaction/1`) — тот же приём использует Ecto; иначе соединение пришлось бы передавать через все доменные функции.

## 3. Свой SQL-мигратор

**Статус:** Принято.

~130 строк вместо ecto_sql. Миграции — чистые SQL-файлы, выполняются через simple query protocol, поэтому в одном файле можно писать функции и триггеры, а файл применяется атомарно. Только вперёд.

## 4. Идентификаторы — UUIDv7

**Статус:** Принято, уточнялось на месте.

Тип `uuid`, `DEFAULT uuidv7()` (встроена в PostgreSQL 18), во всех таблицах с суррогатным ключом.

- Последовательный id раскрывает объёмы: `/transactions/1042` говорит, сколько операций во всей системе. Доступа это не даёт, но информация лишняя.
- UUID может сгенерировать клиент (офлайн-ввод, черновики AI-ввода). Операцию можно провести с `id` от клиента; принимается только UUIDv7, чтобы вставки оставались упорядоченными. Занятый `id` — конфликт (`id_taken`, 409), а не возврат существующей операции: повтор без риска дубля обеспечивает `idempotency_key`, а `id` от клиента как ключ идемпотентности не используется.
- v7, а не v4: v7 упорядочен по времени, вставки идут в конец B-tree индекса, как у bigint; v4 разбрасывает их по индексу. Внутри одного соединения PostgreSQL 18 генерирует v7 монотонно, поэтому проводки одной операции упорядочены по id в порядке вставки.
- 16 байт против 8 для объёмов личных финансов несущественны. Смешивать типы (bigint для `ledger_entries`, которые не видны снаружи) ради этой экономии не стали.
- `idempotency_key` не совмещён с первичным ключом: ключ приходит от клиента, и первичным ключом его делать не стоит.

**UUID в коде — строки, а не 16-байтные binary.** Postgrex без Ecto работает с uuid как с 16 байтами. Вместо преобразования на границе HTTP (каждый id в каждом ответе и каждом параметре) зарегистрирован свой Postgrex-тип (`Networth.DB.UUID` в `Networth.DB.Types`): кодирование и декодирование происходят в одном месте, весь код видит одну форму — каноническую строку. Входные id проверяет `Params.cast_id/1`; строка, не являющаяся UUID, превращается в 404/422 до запроса к БД.

Рассматривали bigint `GENERATED ALWAYS AS IDENTITY` (был в первой версии схемы) — отклонён по причинам выше.

## 5. Деньги — bigint минимальных единиц, точность из справочника валют

**Статус:** Принято.

Целые числа не теряют точность и быстро суммируются. `numeric` тоже точен, но не хранит смысл «минимальная единица валюты», и через него проще случайно сохранить 0.001 USD. Точность валюты — в `currencies.exponent`, не предполагается 2 знака. Внешний формат — десятичная строка, числа JSON отклоняются: float уже мог потерять точность на клиенте.

## 6. Double-entry: суммы со знаком

**Статус:** Принято.

Одна колонка `amount` (дебет +, кредит −) вместо пары `debit/credit` или `amount + direction`. Инвариант баланса — просто `sum(amount) = 0`, баланс счёта — `sum(amount)`. Знак при показе пользователю определяется `kind` счёта.

## 7. Категории — измерение на строках расхода/дохода, а не счета ledger

**Статус:** Принято, уточнялось на месте.

**Где категория в ledger**:

- *Категория = счёт ledger* (как в GnuCash): «Еда» — expense-счёт. Счёт имеет одну валюту, значит «Еда» нужна в каждой валюте, подкатегории превращаются в дерево счетов, переименование/архив категории — операция над ledger. Отклонено.
- *Ledger использует системные счета income/expense на валюту, категория — аналитическое измерение* (выбрано). Ledger отвечает за деньги, категории — за аналитику; категории свободно переименовываются и архивируются.

**Где категория в операции** (split, чек «еда + бытовая химия»):

- *A. Одна категория на операцию* (было в первой версии). Чек приходится вводить двумя операциями, которые не совпадают со списанием в выписке банка; исправление — два сторно.
- *B. Категория на строке* (выбрано). `category_id` стоит на проводках по счетам `expense`/`income`, по одной на строку; счёт оплаты получает одну проводку на всю сумму. Отдельной таблицы строк нет: строка и есть проводка, суммам негде разойтись.

Последствия B:
- сторно копирует категории с обратным знаком, поэтому сумма проводок по категории сама учитывает исправления;
- отчёты по категориям считаются по `ledger_entries.category_id`;
- категория — часть неизменяемой проводки: изменить её можно только сторно и новой операцией;
- соответствие категории счёту проверяет БД: на проводке хранится `account_kind` (подтверждён FK на счёт), и FK на категорию по `(workspace_id, category_id, account_kind)` не пропускает категорию на счёте карты или income-категорию на счёте `expense`. Это требование «не смешивать операцию и проводки» не нарушает: операция по-прежнему отдельная сущность, теги — на ней.

## 8. Мультивалютность: баланс по каждой валюте, обмен через системные счета exchange

**Статус:** Принято, уточнялось на месте.

Сумма проводок обязана быть нулевой в каждой валюте отдельно. Обмен проходит через счёт `exchange` в каждой из двух валют, курс и обе суммы сохраняются в `exchanges`. Альтернатива — хранить проводки в «базовой валюте» workspace — требует автоматической конвертации, что запрещено требованиями и теряет исходные суммы.

**Комиссия обмена** — необязательная `fee` в валюте источника, сверх `from_amount`: две дополнительные проводки той же операции, `expense[c1] +fee` (с необязательной категорией) и `A −fee`. Это обычная строка расхода, поэтому отчёты по категориям и сторно учитывают её без отдельной логики. Сумма хранится в `exchanges.fee_amount`; курс считается по суммам обмена без комиссии. Комиссия в валюте получения (обменник выдаёт меньше) отдельно не моделируется: пользователь вводит фактически полученную сумму, разница остаётся в курсе.

## 9. Балансы вычисляются из проводок

**Статус:** Принято.

Нет хранимого баланса — нечему расходиться с ledger, и конкурентные проводки не требуют блокировок строк счетов. Индекс `ledger_entries (account_id) INCLUDE (amount)` делает подсчёт дешёвым на объёмах личных финансов. Если понадобится, следующий шаг — периодические снимки балансов (balance snapshots), а не мутируемый счётчик.

## 10. Неизменность и сторно

**Статус:** Принято, уточнялось на месте.

Операции, проводки и детали обмена неизменяемы на уровне БД. Исправление — сторно (зеркальные проводки с теми же категориями, ссылка на исходную) и новая операция. Сторно запрещено сторнировать, чтобы цепочки не ветвились — для «отмены отмены» операцию вводят заново.

**Дата сторно по умолчанию — дата исходной операции.** Сторно у нас означает «запись была ошибкой», поэтому отчёт за период исходной операции должен исправиться. Закрытых периодов в личных финансах нет; момент исправления виден по `inserted_at`. Альтернатива — датировать сегодняшним днём (как в бухгалтерии с закрытыми периодами) — оставляет ошибку в отчёте прошлого месяца. Клиент может передать дату явно. Возврат товара — не сторно, а доход с категорией Refunds.

**Повторное сторно возвращает существующее сторно**, а не ошибку: ретрай клиента, не получившего ответ, должен получить тот же результат. Двойное сторно невозможно (уникальный индекс по `reverses_id`, `FOR UPDATE` на исходную операцию).

Теги можно менять у проведённой операции: они не влияют на деньги и явно исключены из ledger требованиями. Описание тоже можно менять, с журналом (решение 23). Категории, суммы, счета и дата — только через сторно и новую операцию.

## 11. Инварианты баланса — в БД, отложенными триггерами

**Статус:** Принято.

Проверка в коде недостаточна: любой будущий код или ручной SQL может записать несбалансированные проводки. Отложенный constraint trigger проверяет операцию при COMMIT, когда все проводки уже записаны.

## 12. Изоляция workspaces: Scope + составные FK

**Статус:** Принято.

Доступ к данным workspace только через `%Scope{}` из `Workspaces.authorize/2`, и все запросы фильтруют по `scope.workspace_id`. Дополнительно составные FK с `workspace_id` не дают записи сослаться на объект чужого workspace, даже если в коде будет ошибка. Row Level Security PostgreSQL не используется: потребовал бы передачи пользователя в сессию БД при каждом запросе; при необходимости можно добавить позже.

Чужой workspace возвращает 404, а не 403, чтобы не раскрывать существование.

## 13. Отрицательные балансы разрешены

**Статус:** Принято.

Учёт отражает реальность, а не управляет ею: если наличные «ушли в минус», значит, какая-то операция не записана. Блокировка такой записи мешала бы вводу в произвольном порядке и потребовала бы сериализации проводок по счёту.

## 14. Идемпотентность по ключу клиента со сверкой параметров

**Статус:** Принято, уточнялось на месте.

Уникальный индекс `(workspace_id, idempotency_key)` и `INSERT … ON CONFLICT DO NOTHING`: при конкурентном повторе второй запрос дождётся первого и вернёт его операцию. Вместе с ключом хранится `idempotency_hash` — SHA-256 параметров запроса (`:erlang.term_to_binary(params, [:deterministic])`). Повтор с тем же ключом и другими параметрами — `{:error, :idempotency_key_reused}` (HTTP 409): иначе клиент с ошибкой генерации ключей молча получил бы чужую операцию вместо проведения новой.

Сверяется точное содержимое: `"100"` и `"100.00"` — разные запросы. Ретрай отправляет те же байты, так что это не мешает.

Ключ не совмещён с первичным ключом операции (см. 4). Тот же механизм — у создания счёта.

`ON CONFLICT` срабатывает только на индексе ключа. Одновременный повтор может раньше столкнуться с другим уникальным индексом — первичным ключом (если клиент передал свой `id`) или именем счёта — и получить `id_taken` / «имя занято». Поэтому такая ошибка при переданном ключе превращается в повтор, если запись с этим ключом уже есть. Гонку ловят тесты с одновременными запросами.

## 15. Аутентификация: PBKDF2 из :crypto и непрозрачные bearer-токены

**Статус:** Принято.

PBKDF2-HMAC-SHA256, 600 000 итераций (OWASP), соль 16 байт — встроено в OTP, без NIF-зависимостей bcrypt/argon2. Формат хэша содержит число итераций, поэтому его можно повысить без миграции. Токен — 32 случайных байта, в БД только SHA-256, срок 30 дней. Отзыв — удаление строки. JWT не нужен: проверка всё равно идёт в БД.

## 16. Приглашения по email без отправки писем

**Статус:** Принято.

Приглашение адресовано email; принять может только пользователь с этим email. Писем нет — приглашённый видит их в API. Токен-ссылки и истечение срока — когда появится отправка писем.

## 17. Тесты на реальной БД с TRUNCATE

**Статус:** Принято.

Без Ecto нет SQL sandbox. Тесты с БД работают последовательно, таблицы очищаются `TRUNCATE` перед каждым тестом. Это позволяет честно тестировать конкурентность (несколько процессов, несколько соединений), чего sandbox в транзакции не даёт.

## 18. Часовой пояс — у workspace

**Статус:** Принято, уточнялось на месте.

`workspaces.timezone` (IANA, по умолчанию `UTC`, проверяется по `pg_timezone_names`). Используется для «сегодня» по умолчанию (`occurred_on` операции, `opened_on` начального остатка) и в будущем — для границ периодов в отчётах.

У workspace, а не у пользователя: семейный workspace — общий журнал, и «ноябрь» должен быть одинаковым для всех участников, где бы они ни находились. Клиент по-прежнему может и должен передавать `occurred_on` сам — он знает, что значит «вчера» для пользователя; часовой пояс нужен, когда даты нет.

Дата считается в PostgreSQL (`now() AT TIME ZONE tz`) — у него своя база часовых поясов, зависимость `tzdata` для Elixir не нужна.

## 19. Граница ядра; AI-ввод — отдельный клиент

**Статус:** Принято.

Финансовое ядро (`Ledger`, `Accounts`, `Categories`, `Tags`, `Workspaces`) не зависит от HTTP: принимает `Scope` и map параметров, возвращает данные или ошибку. HTTP — один из клиентов. Будущий AI-ввод встраивается так же:

1. Адаптер получает текст и контекст workspace (`Accounts.list/1`, `Categories.list/1`, `Tags.list/1`).
2. Провайдер возвращает предложение в формате параметров `Ledger.post/2`; неоднозначные поля остаются пустыми.
3. Пользователь подтверждает предложение.
4. Подтверждение — обычный `Ledger.post/2` с той же валидацией и с `idempotency_key`.

AI не получает доступ к БД и не строит проводки. Специального кода под AI в ядре нет и не нужно.

## 20. Конкурентность без блокировки балансов

**Статус:** Принято.

Уровень изоляции — READ COMMITTED. Корректность обеспечивают не блокировки счетов, а:

- балансы вычисляются из неизменяемых проводок (решение 9), поэтому одновременные проводки не могут «потерять» обновление;
- уникальные индексы: однократное сторно, `idempotency_key`, один системный счёт на тип и валюту (создаётся через `INSERT … ON CONFLICT DO NOTHING`, затем `SELECT`);
- `FOR UPDATE` на сторнируемую операцию — второе сторно ждёт и видит первое;
- `FOR SHARE` на счета при проведении — архивирование счёта не пересекается с проводкой по нему.

Нарушение отложенного constraint trigger обнаруживается при COMMIT, и DBConnection в этом случае бросает исключение, а не возвращает `{:error, _}`. Код таких проводок не строит, так что это ошибка программы, а не пользовательского ввода.

## 21. Документация: README, DOMAIN, DECISIONS, ROADMAP, AGENTS

**Статус:** Принято, уточнялось на месте.

Схема БД описана только в миграциях: отдельный документ дублировал бы SQL и расходился с ним. Устройство кода и список API — в README, финансовая модель и инварианты — в DOMAIN. Отказались от PRODUCT, ARCHITECTURE и DATA_MODEL как от лишних на этом этапе.

Правила работы (порядок начала сессии, что обновлять после задачи, принципы, соглашения кода) — в AGENTS.md, а не в разовых промптах: иначе следующая сессия о них не узнает. CLAUDE.md только импортирует AGENTS.md (`@AGENTS.md`), чтобы правила жили в одном месте для любых агентов.

## 22. Отчёты считаются из проводок при каждом запросе

**Статус:** Принято.

Без материализованных агрегатов и снимков: суммы по индексам `ledger_entries` на объёмах личных финансов дешёвые, а любой кэш пришлось бы поддерживать согласованным с ledger (решение 9). Если запросы станут медленными, следующий шаг — помесячные снимки, а не изменяемые счётчики.

Период фильтруется по `occurred_on`, а не по `inserted_at`: отчёт отвечает на вопрос «сколько потрачено в октябре», а не «сколько записано в октябре». Часовой пояс для этого не нужен — дата уже в календаре workspace (решение 18).

Разбивка по категориям строится из `ledger_entries.category_id` (решение 7), поэтому сторно, split и подкатегории не требуют отдельной логики. Подкатегории сворачиваются в родителя в Elixir, а не в SQL: дерево всего в два уровня, и категорий в workspace немного.

## 23. Описание операции редактируется, изменения пишет журнал в БД

**Статус:** Принято; хранение журнала частично заменено №32 (общий журнал активности вместо `transaction_changes`).

Опечатка в описании не влияет на деньги, а исправлять её через сторно (три записи в истории ради одного слова) неудобно. Поэтому описание — единственное изменяемое поле операции.

**Варианты**:
- *Только сторно и новая операция* — строго, но неудобно для повседневного ввода. Отклонено.
- *Изменение с журналом, журнал пишет приложение* — журнал можно обойти любым `UPDATE` мимо `Ledger.update/3`.
- *Изменение с журналом, журнал пишет триггер* (выбрано). Триггер `transactions_guard` разрешает `UPDATE` только колонки `description` (сравнение `to_jsonb(NEW) - 'description'` со старой строкой, поэтому новые колонки автоматически остаются неизменяемыми) и сам пишет событие `transaction.description_changed` в журнал активности (решение 32; до него — в отдельную таблицу `transaction_changes`). Автора берёт из локальной для транзакции настройки `networth.user_id` (`set_config(..., true)`), которую ставит приложение; без неё изменение отклоняется. Журнал только дополняется.

Одновременные правки сериализуются блокировкой строки, поэтому история правок — непрерывная цепочка: старое значение каждого события равно новому значению предыдущего.

Изменения тегов пишутся в журнал активности приложением (`transaction.tags_changed`), без гарантии со стороны БД: на деньги и отчёты они не влияют.

## 24. Хотя бы один owner — проверка в БД с блокировкой workspace

**Статус:** Принято.

Правило «у workspace есть owner» нарушается гонкой: два owner одновременно выходят, каждый видит второго и проходит проверку. Простая проверка в приложении или в триггере без блокировки этого не ловит (тест `the database keeps an owner under concurrent raw deletes` падает без блокировки).

Отложенный constraint trigger на `workspace_members` перед проверкой берёт `FOR UPDATE` на строку workspace: второе изменение ждёт коммита первого и видит его результат. Функции `Workspaces.update_member/3` и `remove_member/2` берут ту же блокировку в начале транзакции — так пользователь получает понятную ошибку `last_owner` (HTTP 409), а триггер остаётся страховкой для любого другого пути.

Ролей по-прежнему две, все owner равны: любой owner может менять роли и удалять других owner, пока остаётся хотя бы один. Отдельной операции «передать владение» нет: назначить owner другого и затем стать member.

## 25. Пагинация истории по курсору

**Статус:** Принято.

`offset` на длинной истории медленный (БД читает и отбрасывает пропущенные строки) и неустойчив: операция, добавленная между запросами страниц, сдвигает выдачу, и строки повторяются или пропадают. Курсор — пара `(occurred_on, id)` последней строки страницы (base64url, для клиента непрозрачен); следующая страница — `(occurred_on, id) < курсор` по тому же индексу `(workspace_id, occurred_on DESC, id DESC)`. `id` разрешает ничьи по дате.

Запрашивается `limit + 1` строк: лишняя показывает, есть ли следующая страница, так что последняя страница возвращает `next_cursor: null` без пустого дополнительного запроса.

## 26. Долги — счета, а не отдельная сущность

**Статус:** Принято.

Ledger уже различает активы и обязательства, поэтому личный долг — счёт `receivable` (актив) или `payable` (обязательство) с именем контрагента. Выдача, возврат и получение долга — переводы, прощение — расход со счёта долга. Остаток, история и учёт в капитале получаются без нового кода. Банковские кредиты остаются `loan`.

Отдельная сущность «долг» со сроком, процентами и графиком платежей отклонена как преждевременная; если понадобится, её можно добавить поверх счёта (например, срок возврата как атрибут счёта), не меняя проводки.

Вид счёта вычисляется из типа генерируемой колонкой; новые типы добавлены через `ALTER COLUMN ... SET EXPRESSION` (PostgreSQL 17+).

## 27. Бюджеты: месячный лимит на категорию с историей

**Статус:** Принято.

Лимит — строка `(категория, валюта, месяц начала, сумма)`; действующий лимит месяца — строка с самым поздним `starts_on` не позже этого месяца. Изменение лимита с какого-то месяца не переписывает прошлые месяцы. Отдельной таблицы «история» нет: история и есть строки.

Факт берётся из `Reports.income_expense/2`, а не отдельным SQL: правила подсчёта (подкатегории, сторно, split, комиссии) одни для отчётов и бюджетов.

Сознательно не сделано (по умолчанию, согласовано): недельные и годовые периоды, перенос остатка, общий бюджет без категорий, бюджеты доходов. Модель расширяется без миграции данных: период и перенос — новые колонки с текущим поведением по умолчанию.

## 28. Ограничение попыток входа — счётчики в памяти узла

**Статус:** Принято.

`Users.login/3`: не больше 5 неудачных попыток на email за 15 минут (подбор пароля к конкретному аккаунту; успешный вход сбрасывает счётчик) и не больше 20 попыток с одного адреса за 5 минут (перебор по многим аккаунтам). При превышении — `{:error, {:rate_limited, seconds}}`, HTTP 429 с `retry-after`, пароль не проверяется. Лимиты — в `config :networth, :login_limits`.

Счётчики — фиксированные окна в ETS (`Networth.RateLimit`), без зависимостей и без записи в БД на каждую попытку. Ограничения: у каждого инстанса свои счётчики (при N инстансах лимит фактически в N раз выше), после перезапуска они обнуляются. Для одного узла этого достаточно; при горизонтальном масштабировании счётчики переносятся в PostgreSQL или общий кэш.

Адрес клиента — `conn.remote_ip`. За обратным прокси это адрес прокси: нужно доверять `X-Forwarded-For` только от известного прокси, это не сделано.

## 29. Исправление и удаление поверх сторно

**Статус:** Принято.

Пользователь ждёт «исправить» и «удалить», а ledger умеет только добавлять. Операции удобства не меняют модель, а собирают её шаги:

- **Исправить** — сторно и новая операция в одной транзакции БД, новая ссылается на исходную через `replaces_id` (уникален: заменить можно один раз). Исходная блокируется `FOR UPDATE`, поэтому из одновременных исправлений проходит одно, остальные получают `already_reversed`; с `idempotency_key` повтор возвращает уже сделанное исправление. Ключ сверяется с тем, что прислал клиент, а не с подставленными значениями по умолчанию.
- **Удалить** — сторно.
- **История** по умолчанию скрывает отменённые пары; полная — по `include_reversed`.

Отклонено: изменяемые суммы в проводках (решение 10) и мягкое удаление флагом (`deleted_at`) — флаг пришлось бы учитывать в каждом запросе балансов и отчётов, а сторно учитывается само.

## 30. Сверка баланса — отдельный тип операции через equity

**Статус:** Принято.

`adjustment` проводит разницу между фактическим и учтённым балансом через системный счёт `adjustment` (equity), а не через расход: неизвестно, на что ушли деньги, и придуманный расход исказил бы отчёты. Вариант «записать разницу как расход с выбранной категорией» не сделан — пользователь может просто записать расход.

Сверка идемпотентна по смыслу: она задаёт целевой баланс, а не сумму, поэтому повтор находит нулевую разницу и ничего не проводит. Счёт блокируется `FOR UPDATE` (проводки берут `FOR SHARE`), чтобы между подсчётом разницы и записью не прошла другая проводка.

## 31. Удаление workspace — отложенное и единственное физическое

**Статус:** Принято.

Отдельные операции не удаляются (решение 29), но «начать заново» и «удалите мои данные» требуют настоящего удаления. Оно делается только целым workspace:

- owner, подтверждение точным именем, задержка 7 дней с отменой — защита от ошибки и от злоупотребления чужим токеном;
- ежечасная задача (`Networth.Maintenance`) удаляет просроченные workspace в одной транзакции на каждый; строка workspace блокируется `FOR UPDATE`, что не даёт параллельно добавить ссылающиеся на него записи и заново проверяет, не отменено ли удаление;
- append-only триггеры пропускают `DELETE` только строк того workspace, id которого записан в локальной для транзакции настройке `networth.purge_workspace`. Альтернатива `session_replication_role = replica` отключила бы все триггеры и проверки внешних ключей и требует прав суперпользователя — отклонена.

Удаление аккаунта пользователя пока не сделано: его нужно связать с удалением workspace, где он единственный owner.

## 32. Журнал активности: семантические события в транзакции изменения

**Статус:** Принято.

**Варианты** (как это делают зрелые системы):
- *Триггерный аудит строк* (pgaudit, supa_audit): обойти нельзя, но фиксирует «изменилась строка», а не «что сделал человек»; ленту для людей из этого не построить, много шума.
- *Семантические события из приложения* (GitHub audit log, Stripe events, PaperTrail): осмысленные действия, но запись можно забыть.
- *Event sourcing / CDC*: для нашей задачи чрезмерно.

**Выбрано — гибрид.** Одна таблица `activity_log`: `кто · действие (resource.verb) · объект · changes {поле: [было, стало]} · data (снимок для отображения) · когда`. Доменные функции пишут событие через `Activity.record/5` **в той же транзакции БД**, что и изменение: событие есть ровно тогда, когда изменение закоммичено (ошибки и пустые изменения событий не оставляют — это проверяют тесты). Единственное изменение ledger, которое разрешено после проведения, — описание операции — по-прежнему записывает **триггер БД**, теперь в общий журнал, поэтому его нельзя сделать бесследно. Журнал только дополняется; удаляется вместе с workspace.

Снимок в `data` (имена, суммы строками с валютой) делает ленту читаемой без подгрузки объектов и сохраняет смысл после их переименования. Денежные действия (проведение, удаление, исправление, сверка) тоже пишутся в журнал, чтобы лента была полной, хотя сами операции и так неизменяемы.

Отдельная таблица `transaction_changes` (решение 23) влилась в журнал миграцией с переносом данных; эндпоинт `/transactions/:id/changes` заменён `/activity?subject_id=`.

Не входит в журнал: вход в систему и прочие события безопасности аккаунта (это отдельный журнал пользователя, не workspace), а также секреты.

## 33. Раскладка кода: контексты, части — в папке по мере роста

**Статус:** Принято.

Рассмотрены: плоская раскладка (была), слои `domain/infra/web` (размазывает одну функциональность по папкам, против духа проекта), umbrella-приложения (граница ядра и HTTP через компилятор, но лишние конфиги и сборка для одного приложения), контексты в стиле Elixir/Phoenix.

Выбраны контексты, точечно: модуль контекста — публичный API (`Networth.Ledger.post/2` и т. д.), его части — в одноимённой папке, и только когда модуль разросся. Разбиты `ledger.ex` (890 строк → API + posting, reversal, correction, adjustment, editing, history) и `workspaces.ex` (members, invitations, deletion); инфраструктура БД собрана в `db/`. Маленькие контексты (accounts, tags, budgets, …) остаются одним файлом. Роутер пока целиком; при росте — `forward` на роутеры по ресурсам.

## 34. Миграции схлопнуты в базовую схему до первого развёртывания

**Статус:** Принято.

12 миграций, написанных по ходу разработки (функции, переопределённые по три раза, `ALTER` типов, таблица `transaction_changes`, созданная и удалённая), заменены четырьмя файлами с финальной схемой: пользователи и workspaces, счета/категории/теги, ledger, бюджеты и журнал. Эквивалентность проверена сравнением `pg_dump --schema-only` баз, собранных из старых и новых миграций: отличается только порядок колонок (`inserted_at` последней, `replaces_id` рядом с `reverses_id`).

Пока развёрнутых баз нет, так можно; после первого развёртывания миграции только добавляются новыми файлами (AGENTS.md).

## 35. Ошибки валидации — коды с деталями, все поля сразу

**Статус:** Принято.

Было: первая ошибка английской фразой (`"must be a decimal string"`). Интерфейс на другом языке не может перевести свободный текст, а форма подсвечивала поля по одному за отправку.

Стало: ядро возвращает `%{"field" => %{code: :too_many_decimals, currency: "JPY", decimals: 0}}` — стабильный код и данные для подстановки, без текста. Английское сообщение по умолчанию добавляет HTTP-слой (`Web.Serializer.validation_errors/1`); клиент переводит по коду. Независимые поля проверяются вместе (`Params.all/1`) и возвращают все ошибки; зависимые (сумма требует валюты счёта, строки split требуют корректных общих полей) — следующим шагом.

Отклонено: тексты на нескольких языках в ядре — язык интерфейса не забота ядра; Ecto-changeset ради накопления ошибок — зависимость и второй способ валидации рядом с `Params`.

## 36. HTTP-слой: два роутера, аутентификация в plug-ах, токен по умолчанию

**Статус:** Принято.

Единый роутер на 480 строк повторял в каждом маршруте обёртку «проверь токен и членство» и смешивал маршрутизацию, аутентификацию и формирование ответов. Теперь:

- `Web.Router` — публичные маршруты и маршруты пользователя; всё внутри workspace уходит `forward "/api/workspaces/:wid"` в `Web.WorkspaceRouter`, где plug `authorize_workspace` до любого маршрута кладёт `scope` в `conn.assigns`. Забыть проверку доступа в новом маршруте нельзя.
- Токен проверяется для **всех путей, кроме явного списка публичных** (`Web.Auth`): новый маршрут защищён по умолчанию, открыть его можно только осознанно. Неизвестный путь без токена — 401, а не 404.
- `Web.Response` — отправка JSON и единственное место соответствия ошибок ядра статусам HTTP; списки и страницы с курсором собираются одинаково.

Отдельной папки `plugs/` нет: оба plug-а — одно понятие (аутентификация) в `web/auth.ex`. Роутеры по ресурсам — когда `WorkspaceRouter` вырастет.

## 37. Имена HTTP-слоя: Serializer и семейство send_*

**Статус:** Принято.

Модуль, придающий данным ядра форму ответа, назывался `Web.JSON` (по формату) и использовался как `View` (через `as:`, чтобы не перекрыть встроенный `JSON` из Elixir 1.18): одна вещь под двумя именами. Теперь — `Web.Serializer`: устоявшийся в API-мире термин для этой роли (Rails, DRF, NestJS), без оттенка шаблонов, как у `View`.

Функции `Web.Response` названы глаголами с общим префиксом, согласованным с `Plug.Conn.send_resp/3`: `send_json`, `send_result`, `send_list`, `send_page`, `send_empty`, `send_error`. Прежнее `render` пришло из Rails/Phoenix, где означает отрисовку шаблона, — у нас шаблонов нет. `send_response` отклонено как слишком похожее на `send_resp`.

## 38. Сущности ядра — структуры, ошибки и ответы — нет

**Статус:** Принято.

Ядро возвращало сущности «голыми» map из SQL: форма счёта или операции нигде не описана, опечатка в ключе всплывает во время работы. Теперь центральные сущности — структуры с `@type t` в папке своего контекста: `Users.User`, `Workspaces.{Workspace, Member, Invitation}`, `Accounts.Account`, `Categories.Category`, `Tags.Tag`, `Budgets.Budget`, `Ledger.{Transaction, Entry, Exchange}`, `Activity.Event`. Запросы собирают их через `DB.all/3`/`DB.one/3`, где `struct!/2` падает на колонке, которой нет в структуре, — запрос и структура не разойдутся незаметно. Тест `entities_test.exs` проверяет, что публичные функции возвращают структуры.

Не структуры:
- **отчёты** — вычисленные сводки без жизненного цикла, map;
- **ошибки** — ожидаемые доменные ошибки в Elixir выражают кортежами (`{:error, :not_found}`, `{:error, {:invalid, ...}}`); структуры ошибок нужны для исключений (`raise`), а доменных исключений нет;
- **ответы** — `Web.Serializer` превращает структуры в map для JSON, промежуточный тип ответа был бы лишним слоем.

Внутренние формы, которые не покидают модуль (строки для вставки проводок, блокировка операции), остаются map.

## 39. Монорепо: server/ и будущий web/

**Статус:** Принято.

Сервер и веб-клиент живут в одном репозитории: `server/` (Elixir), `web/` (клиент, появится), общие `docs/`, `AGENTS.md`, `docker-compose.yml`. Пока API меняется вместе с клиентом, правка обеих сторон — один коммит без промежуточного состояния «клиент ждёт невыкаченный сервер»; спецификация API лежит рядом с обоими; агенты видят обе стороны и общие правила.

Раздельные репозитории оправданы при разных командах, нескольких независимых клиентах или стабильном внешнем API — сейчас ничего из этого нет; разделить монорепо проще, чем свести два.

Следствие для браузера: веб и API отдаются с одного домена (в разработке Vite проксирует `/api`), поэтому CORS не нужен, а вход через HttpOnly-cookie становится естественным вариантом (решается вместе с клиентом).
