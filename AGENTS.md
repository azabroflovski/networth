# Правила работы в репозитории

Для coding-агентов и людей. Что за продукт и как устроена финансовая модель — в README и `docs/`.

## Начало сессии

1. Прочитать README.md, docs/DOMAIN.md, docs/DECISIONS.md, docs/ROADMAP.md.
2. Код — источник правды. Если документация ему противоречит, сначала проверить код, потом исправить документ.
3. По ROADMAP определить, что сделано и какой этап текущий, и продолжать с него.

## После каждой значимой задачи

- `mix test`, `mix format`, `mix compile --warnings-as-errors`. Тестам нужна PostgreSQL (README).
- Обновить DOMAIN, если менялась модель; DECISIONS — новое решение отдельным пунктом с причиной и рассмотренными вариантами; прежние решения не переписывать, у заменённого меняется только статус; ROADMAP — сделанное, следующие задачи, ограничения.
- Не описывать нереализованное как работающее. Не заявлять, что что-то работает, без проверки.

## Принципы

- Приоритет: корректность финансовых данных, затем простота, затем удобство.
- Минимум зависимостей; стандартные средства языка раньше сторонних библиотек.
- Обычные модули и функции. Паттерны, интерфейсы и слои — только когда решают конкретную задачу; без DDD, CQRS, Repository ради них самих.
- Не проектировать под гипотетические требования, не дублировать логику, не добавлять функциональность сверх текущего этапа.
- Не переписывать работающий код ради личных предпочтений.
- Без длинных комментариев, очевидных пояснений и пустых TODO — ни в коде, ни в документации.

## Соглашения кода

- Раскладка: модуль контекста (`Networth.Ledger`, `Networth.Workspaces`) — публичный API. Когда файл разрастается (ориентир — 400–500 строк), части уходят в одноимённую папку (`ledger/correction.ex` → `Networth.Ledger.Correction`), а контекст делегирует им; вызывающий код не меняется. Папки заранее не заводить. Тесты повторяют раскладку `lib/`.
- Модулей и папок `Utils`/`Helpers` не заводить: общая функция принадлежит понятию (`Money.format/2`, `Params.cast_id/1`, `DB.where/3`), папка группирует части одного понятия, а не файлы «одного сорта». Хелперы тестов — в `test/support/`.
- HTTP тонкий: маршрут вызывает доменную функцию и отправляет результат (`Web.Response`: `send_result`, `send_list`, `send_page`, `send_empty`, `send_error`; форма данных — `Web.Serializer`). Правил в роутерах нет. Маршрут внутри workspace — в `Web.WorkspaceRouter`, `scope` берётся из `conn.assigns`. Любой путь требует токен, кроме явного списка публичных в `Web.Auth`; новая доменная ошибка — новый статус в `Web.Response.send_error/2`.
- Данные workspace — только через `%Scope{}` из `Workspaces.authorize/2`; каждый запрос фильтрует по `scope.workspace_id`.
- Внешний ввод — map со строковыми ключами, проверка через `Networth.Params`. Результаты: `{:ok, v}`, `:ok`, `{:error, {:invalid, %{"field" => %{code: :atom, ...детали}}}}`, `{:error, :not_found | :forbidden | ...}`.
- Ошибка валидации в ядре — код и детали (`Params.invalid(field, :too_long, %{max: 100})`), без текста. Текст — только в HTTP-слое: словарь `Web.ErrorMessages`; новый код — новая строка там. Независимые поля проверяются вместе через `Params.all/1`, чтобы клиент получил все ошибки сразу.
- Явный SQL через `Networth.DB`; запись нескольких строк — внутри `DB.transaction/1` (или `DB.transact/1` для функций с `{:ok, _} | {:error, _}`).
- `DB.transaction/1` держит соединение в словаре процесса: запросы из другого процесса (`Task`, `spawn`) внутри транзакции пойдут мимо неё, отдельным соединением. Внутри транзакции не порождать процессы, работающие с БД.
- Сущности ядра — структуры в папке своего контекста (`Networth.Ledger.Transaction`, `Networth.Accounts.Account`, …) с `@type t`. Запрос, возвращающий сущность, собирает её через `DB.all/3` / `DB.one/3` с модулем структуры: лишняя колонка падает сразу. Вычисленные сводки (отчёты) — обычные map. Ошибки — кортежи `{:error, ...}`, не структуры.
- Деньги — integer минимальных единиц, наружу — десятичные строки. Float нигде.
- Id — UUIDv7, в коде строки.
- Ограничение целостности, которое можно выразить в БД, выражается в БД.
- Любое изменение данных workspace пишет событие `Activity.record/5` в той же транзакции БД (`DB.transaction/1` или `DB.transact/1`); пустое изменение события не пишет. Новый вид изменения — новое действие `resource.verb` и тест в `activity_test.exs`.

## Финансовая модель

Инварианты из DOMAIN («Финансовые инварианты») не ослабляются: ledger append-only, исправление только сторно, баланс в каждой валюте, данные изолированы по workspace. Изменение модели — сначала варианты и последствия владельцу проекта, после согласия — запись в DECISIONS.

Прочие технические вопросы решаются самостоятельно и прагматично.

## Миграции и данные

- `priv/migrations/NNNN_name.sql`. Пока нет развёрнутых баз, миграции правятся на месте и применяются через `mix db.reset`; после первого развёртывания — только новыми файлами.
- Destructive-операции с существующими данными — только с явного разрешения.

## Тесты

ExUnit на реальной PostgreSQL, без моков БД. Тестировать поведение, а не реализацию. Тесты ядра используют `Networth.DataCase`, HTTP-тесты — `Networth.ConnCase` (`request/4`, `register/1`) и лежат в `test/networth/web/` по областям. Тесты с БД не запускаются параллельно: перед каждым очищаются все таблицы, кроме справочников (список берётся из базы).
